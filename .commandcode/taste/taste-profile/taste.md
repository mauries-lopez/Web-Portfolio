# Taste Profile
- Prefers designs that look **professional and modern** — clean, contemporary aesthetics over trendy or experimental styles. Confidence: 0.7
- Values **intuitive and straightforward** UX that surfaces details clearly; dislikes designs that obscure information behind unnecessary interactions. Confidence: 0.7
- When redesigning, wants to **preserve the existing color palette/style** — evolution over revolution; the new should feel like a refined version of the old, not a departure. Confidence: 0.9
- Favors a balance of **"straightforward and new"** — clean simplicity that still feels fresh, not stale or dated. Confidence: 0.6
- Strongly dislikes designs that feel **"AI-made"** — rejects trendy overused patterns (timeline abstractions, scroll animations, gradient backgrounds, card wrappers) in favor of authentic, restrained design. Confidence: 0.9
- Prefers **simplistic over ornate**: professional and modern but restrained — no excessive styling, decorative motion, or gratuitous depth effects. Confidence: 0.8
- Values **code maintainability through flatness**: each component should own its data inline; adding a new entry (experience, project) should be as simple as copying a JSX block. Rejects wrapper abstractions or layers of indirection that make editing harder. Confidence: 0.9
- **Responsive design is a baseline**, not an afterthought — explicitly expects layouts to adapt across breakpoints (mobile through desktop), not just tolerate smaller screens. Confidence: 0.8
- Enjoys **full-width immersive content sections** that break out of the standard max-width container for visual impact — e.g., auto-scrolling carousels spanning the full viewport. Confidence: 0.7
- When asking for design improvements, uses "modern" to mean **contemporary interaction patterns** (auto-scroll, full-bleed) — not trendy aesthetics or decoration. Wants the content presentation to feel current while the visual style stays restrained. Confidence: 0.6
- Prefers **UI chrome to be proportional and understated** — controls like theme toggles and nav buttons should blend in, not dominate. Rejects oversized touch targets (e.g., 44×44px toggle deemed "too big") in favor of subtle, fitting proportions. Confidence: 0.7
- Prefers **compact, space-efficient mobile layouts** — favors horizontal inline arrangements (photo + name side by side in one row) over stacked vertical layouts that waste screen real estate on small viewports. Has a high bar for compactness; will ask for further reduction even after an initial tightening pass, expecting notably small photos, tight padding, and condensed text on mobile. Confidence: 0.5
- Prefers **unified, single-code-path layouts** across breakpoints — mobile should mirror the desktop design structure (same visual hierarchy, same component structure) rather than using distinct mobile-only layouts with hidden/visible toggling. When mobile needs adaptation, prefer centering and stacking the same elements over rearranging them into a different composition. Explicitly requested this: "mobile can copy the design of desktop but its just centered." Confidence: 0.9
- Engages with **systematic design quality pipelines** — runs smell detection, accessibility checkup, design review, interaction audit, and friction-removal passes as part of UI refinement workflow. Values thoroughness over one-shot fixes. Confidence: 0.6
- Values **functional, purposeful interactivity** — wants the site to feel alive and responsive to user actions (active nav tracking, hover feedback), but this is distinct from purely decorative motion. Interactivity should serve UX, not ornamentation. Reconcilable with the rejection of "AI-made" scroll animations: the latter is about gratuitous decoration, the former about meaningful feedback. Confidence: 0.5
- Dislikes **third-party embeds (iframes) placed inside scrolling carousels** — wants embedded content in a stable, static container outside any auto-scrolling mechanism. Confidence: 0.8
- Prefers **semantic content placement**: content should live in the section it logically belongs to (e.g., a project badge/embed belongs in the Projects section, not the Hero). Explicitly directs where an embed should go ("place it in the Project div inside DateTayo only") rather than leaving placement to the assistant. Confidence: 0.85
- Rejects designs that read as **generic/template portfolio** — beyond avoiding "AI-made" patterns, wants the design to have a distinctive character and point of view, not just clean boxes ("make sure it is not the generic portfolio design"). Confidence: 0.6
- Chose (and approved) a **Swiss-minimal design language**: grid-based layout, bold typography with tight tracking, generous whitespace, numbered/labeled sections, flat surfaces where structural border lines do the work instead of shadows. Character comes from proportion and restraint, not decoration. Confidence: 0.6
- Prefers a **plan-first workflow for significant redesigns** — explicitly asks the assistant to "use a plan" before any implementation, and iterates on the plan (scope, style, structure) before approving execution. Confidence: 0.6
- Values **reusable design-system documentation** — asked for a markdown reference file capturing the theme (colors, dark/light mode toggling, typography, font sizes/styles, responsive behavior, interaction states) so future pages inherit the same visual DNA and stay consistent. Confidence: 0.8

- Prefers **native CSS/platform interaction patterns over JS libraries** — approved a mobile carousel fix built on CSS scroll-snap + native swipe with the marquee animation paused, explicitly avoiding JS handlers or a carousel library in favor of free browser-native behavior. Confidence: 0.5
- Performs **visual QA across every breakpoint** and flags clipped/cut-off content as a defect — expects all elements to render fully and cleanly at each viewport size, reporting specific visual bugs (e.g., a box cut off on desktop view, marquee cards showing incomplete/clipped boxes) tersely for immediate fixing, often volunteering a root-cause hunch ("my hunch is the width") to steer the debug. Confidence: 0.7
- Wants **interactive elements to look clickable** — links/buttons should carry a visually distinct color (and hover feedback like underline) so their affordance is explicit; muted/subtle colors that hide interactivity are rejected. Asked for View All links to be made "more distinct color so it looks like it can [be] clicked." Confidence: 0.6
- Expects **changes to a shared component to propagate to every place it renders** — when a new feature (e.g., a stats/user-count field) is added to a template, it must also appear in all other sections that reuse that same template (e.g., the Marquee section on the homepage), not just the primary page. Explicitly requested this in the latest iteration ("It should also be seen in the Marquee section"). Confidence: 0.7
- Values **social-proof metrics on project cards** — likes surfacing concrete traction data (e.g., "15+ active users") as a highlighted detail, and wants these achievement stats visually **emphasized** so they read as accomplishments. Iterated on the exact treatment until satisfied: from a muted footnote beside the link → a full-width bordered amber block → finally a compact **amber pill chip** (rounded-full, tinted background, bold text, left-aligned under the link). The key invariant is that stats must stand out as achievements, not blend in. Confidence: 0.8
- Prefers **embedded content (iframes) inside a project card to sit directly under the description**, centered, reading as part of the card's content — not relegated to the bottom/footer of the card. When asked, chose "inside card, repositioned" over moving the embed to a separate full-width section below the grid, keeping it semantically attached to its project. Confidence: 0.6
- Expects **cross-page visual consistency** — every subpage must follow the same design language as the main/homepage (same max-w container, numbered amber mono section eyebrows, bold tracking-tight headings, flat bordered surfaces without card wrappers). Flagged the Projects page as wrong when it diverged from Main.tsx ("the whole Projects page does not follow the theme of Main.tsx"), and approved rebuilding it to mirror the homepage's structure exactly rather than inventing its own layout. Confidence: 0.8

- Treats **localStorage as the canonical source of truth for persistent UI state (e.g., theme)** — expects the app to always read from localStorage rather than trust duplicated in-memory state, and considers state that fails to persist across page navigation (theme resetting when switching pages) a bug to fix at the root cause, not a cosmetic issue. Confidence: 0.7
- Expects **hydration-safe SSR code** — flags server/client HTML mismatches ("Hydration failed because the server rendered HTML didn't match the client", attribute-level `<html>` `className` mismatches caused by pre-paint inline scripts) as defects to be fixed at the root cause, so browser-only reads (e.g., `localStorage`) must not run in a way that diverges between server and client render (e.g., using a server snapshot during SSR/hydration rather than reading browser state during initial render). Reported this error a second time after an initial fix, confirming the bar stays strict until the mismatch is fully gone. Confidence: 0.7
